# 审查命令行（agy）的实测行为与排查

这些是在 agy 1.5.6 上实测得到的事实。`scripts/external_review.py` 已经按它们处理；只有脚本报错、或要改脚本时才需要读这里。

## 实测事实

- **斜杠命令在无头模式下有效**。`agy -p "/code-review main ..."` 会展开并执行 code-review 的流程。不要去问模型“你有没有这个 skill”，它的自述不可靠（它会说没有），以实际展开为准。
- **无头模式不能弹权限确认**。清单外的终端命令会被自动拒绝。
- **一条命令被拒，整轮结束**。模型不会收到“被拒”后换个办法继续，而是整个回合直接返回空正文。
- **失败时仍然报告成功**。上述情况下进程退出码是 0，结果里 `status` 是 `SUCCESS`。真正的信号是 `denied_actions` 非空、`response` 为空。
- **`--mode plan` 是只读的**，并且能正常输出审查报告。多次运行后 worktree 的 HEAD、分支、工作区状态都没有变化。脚本仍会在每轮前后比对，作为第二道保险。
- **`--settings` 只对单次调用生效**，不会写进用户的配置文件。
- **耗时**：flash 档约 1.5 分钟、约 15 万 token；carbon 档更慢。脚本默认最多等 30 分钟。
- **并行子代理**：code-review 要求两个轴用并行子代理分别跑。flash 档实测没有这样做，而是在一个上下文里顺序看完。报告结构不受影响。

## 退出码 3：审查没跑完

脚本会在 stderr 里列出原因。常见的三种：

1. **有命令被拒**。stderr 会给出被拒的命令。实测遇到过两类：想自己验证的 `npm run typecheck`，和清单当时没列的只读命令 `git grep`。提示词已经把允许的命令逐个告诉审查者，但它每次的做法不完全一样，偶尔仍会尝试别的。直接重试一次，多数情况下就过了；同一条只读命令反复出现时，见下一节。
2. **正文为空但没有被拒记录**。多半是超时或服务端中断，看同目录的 `round-N.stderr.txt`。重试一次。
3. **正文缺少 `## Standards` 或 `## Spec`**。审查者没按格式输出，无法可靠地分辨阻塞项。重试一次。

重试一次仍失败就停下来告诉用户：哪一轮、什么原因、被拒的是什么命令。不要把它当成零发现，也不要自己通读 diff 来顶替这一轮。

每轮的原始事件流保存在 `round-N.ndjson`，里面有审查者每一步调用了什么工具、跑了什么命令。

## 调整命令放行清单

清单是脚本顶部的 `ALLOWED_COMMANDS`。规则：

- 每一项是“命令加子命令”的前缀，例如 `git diff`；agy 按完整单词匹配。
- 不能用通配。`command(*)` 会被 agy 自己拒绝。
- 只放只读命令。清单是“只读审查”这个承诺的一部分。

如果同一条只读命令反复导致退出码 3（例如某个仓库的审查总要用 `git blame`），把它加进清单是合理的；加之前告诉用户。会写文件、会联网、会执行项目代码的命令不要加。

## 为什么不用 `--dangerously-skip-permissions`

它能让审查一次跑通，但同时放开了写文件和执行任意命令的权限。审查者是另一个模型，在用户的工作目录里运行；“它只读”是用户信任这个流程的前提。宁可偶尔重试，也不放开。

## 为什么审查者不跑类型检查和测试

- 开发方每轮修改后都会按仓库规则跑这些检查，重复跑收益小。
- 放行清单每个仓库不同（`npm`、`pnpm`、`uv`、`cargo`……），漏一条就整轮作废。
- 允许执行项目脚本之后，“只读”就不再有保证：测试和构建脚本可以写任何文件。

所以审查者只做静态审查。

## 其他命令行

目前只适配并实测过 `agy`。`cursor-agent` 的无头参数、权限模型和输出格式没有验证过，脚本不会调用它；`check` 在只找到 `cursor-agent` 时会明确提示这一点。要支持它，需要先像上面这样把它的行为实测一遍，尤其是“失败时怎么表现”。
