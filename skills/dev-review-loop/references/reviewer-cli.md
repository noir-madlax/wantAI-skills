这些是在 agy 1.5.6–1.5.10 上实测得到的事实。`scripts/external_review.py` 已经按它们处理；只有脚本报错、或要改脚本时才需要读这里。

## 实测事实

- **斜杠命令只在 skill 对 agy 可见时才展开**。agy 只在 `~/.gemini/config/skills/<名字>/` 和仓库的 `.agents/skills/<名字>/` 里找 skill，不看 Claude Code 的 `~/.claude/skills`、`~/.agents/skills`。找不到时 `/code-review` 只是一串字面文字，模型会自己发挥：到处找 skill 文件（读仓库外文件被拒）、或者钻进 `.venv` 里读第三方库直到超时（2026-11-18 实测两次）。所以 `check` 和每轮 `run` 都先确认两个依赖 skill 在 agy 的目录里、且 SKILL.md 带 `name` frontmatter（没有的会被 agy 忽略）。不要去问模型“你有没有这个 skill”，它的自述不可靠。
- **展开后，code-review 会开两个并行子代理，子代理收不到本脚本提示词里的约束**。主代理给子代理写的提示词只转述了“只读”，没转述当时的命令清单；子代理照常用 `rg`、`find`，被拒，整轮作废（2026-11-18 第 3 轮实测）。这是去掉 `--mode plan` 的直接原因，见下文。提示词现在要求主代理把约束原样写进子代理的任务说明，但这只是要求，不是保证。子代理的会话记录在 `~/.gemini/antigravity-cli/brain/<主会话 id>/.system_generated/subagents/` 指向的会话目录里，事件流里看不到。
- **无头模式不能弹权限确认**。凡是需要确认的操作都会被自动拒绝。哪些操作需要确认，取决于模式：`--mode plan` 下每条终端命令都要确认；不加 `--mode` 时按用户自己的 agy 设置（自动执行策略）走，`ls`、`rg` 这类普通命令直接执行（2026-11-18 实测）。
- **一条命令被拒，整轮结束**。模型不会收到“被拒”后换个办法继续，而是整个回合直接返回空正文。
- **失败时仍然报告成功**。上述情况下进程退出码是 0，结果里 `status` 是 `SUCCESS`。真正的信号是 `denied_actions` 非空、`response` 为空。
- **`--settings` 只对单次调用生效**，不会写进用户的配置文件。
- **耗时**：同一个小改动（2026-11-18/20 实测）：carbon-low 约 15 分钟、5.8 万 token；neon-high（默认）约 3 分钟、5 万 token，两者都开了并行子代理、报出同样的阻塞项，neon 另多给 3 条判断项。flash 档约 1.5 分钟。脚本默认最多等 60 分钟（`--timeout` 可调）。
- **并行子代理**：code-review 要求两个轴用并行子代理分别跑。skill 能被 agy 看到时，carbon 档会照做（flash 档在 skill 不可见时测的，当时是顺序看完）。去掉 `--mode plan` 后的实测（2026-11-18，carbon-low，小改动）：两个子代理都跑完，用了 `/Library/Developer/CommandLineTools/usr/bin/git` 这种绝对路径和 `ls`，旧清单下都会被拒；埋的两条硬性违规和一条 Spec 缺失全部报出；工作区没被改动。整轮约 15 分钟，时间主要花在模型生成长回复上，不是在等权限。

## 退出码 3：审查没跑完

脚本会在 stderr 里列出原因。常见的三种：

1. **有操作被拒**。stderr 会给出被拒的命令或文件。去掉 `--mode plan` 后普通命令不再需要确认，剩下的多半是读仓库外的文件（见“仓库外的只读放行”），或用户的 agy 设置认为需要确认的命令。子代理里被拒的命令不在事件流里，要去子代理的会话记录里找（见上文）。直接重试一次；同一处反复被拒时停下来告诉用户。
2. **正文为空但没有被拒记录**。多半是超时或服务端中断，看同目录的 `round-N.stderr.txt`。重试一次。
3. **正文缺少 `## Standards` 或 `## Spec`**。审查者没按格式输出，无法可靠地分辨阻塞项。重试一次。

重试一次仍失败就停下来告诉用户：哪一轮、什么原因、被拒的是什么命令。不要把它当成零发现，也不要自己通读 diff 来顶替这一轮。

每轮的原始事件流保存在 `round-N.ndjson`，里面有审查者每一步调用了什么工具、跑了什么命令。

## 为什么不用 `--mode plan`

早期版本用 `--mode plan` 保证审查者只读，再用一张 git 只读子命令清单（`--settings` 里的 `command(...)` 规则）开口子。实际跑下来这条路不通：

- plan 模式下每条命令都要确认，无头模式下等于全部拒绝，只能靠清单逐条放行。
- 模型换个写法（`rg`、`ls`、`find`、`git -C`、把几条命令用 `&&` 串起来）就不在清单里，一条被拒整轮作废。
- code-review 的并行子代理收不到清单，必然越界。

所以现在不加 `--mode`，按用户自己的 agy 设置执行命令，脚本不再维护命令清单。“只读”改成三层：提示词要求只读并转述给子代理；每轮开跑前备份未提交改动；跑完比对内容，被改就作废（退出码 4）。

不加 `--mode` 时，用户 agy 设置认为危险、需要确认的命令（例如删除文件）在无头模式下会怎样，没有实测过；被拒会表现为退出码 3，被放行而改了文件会表现为退出码 4，两种都不会被当成审查通过。

## 审查者改了工作区（退出码 4）

脚本在每轮开跑前把未提交改动备份到 `<out_dir>/round-N.backup/`：

- `tracked.patch`：已跟踪文件相对 HEAD 的改动（`git diff HEAD --binary`）；
- `untracked.tar`：未跟踪、未被忽略的新文件；
- `HEAD`：当时的提交。

跑完发现 HEAD、分支、`git status` 或内容指纹有任何变化，就作废本轮，stderr 给出备份位置和恢复步骤。不要自动恢复：先把差异给用户看，用户同意后再按步骤恢复。恢复第一步是把审查者改出来的状态 `git stash push -u` 留存下来，而不是直接丢掉。

## 仓库外的只读放行

审查者会自己读仓库外的文件，被拒一次整轮就作废。实测（2026-11-18）出现过两种：

- 仓库里没有 `CLAUDE.md` / `AGENTS.md` 时，code-review 找编码规范会退到全局 `~/.claude/CLAUDE.md`；
- agy 会按 diff 自动加载描述匹配的已装 skill（例如 diff 含前端文件时加载 `modern-web-guidance`）。

所以脚本的 `read_rules()` 在运行时生成只读规则，放行：`find_skill` 搜索的各个 skill 根目录、其中软链 skill 的真实目录，以及全局 `~/.claude/CLAUDE.md`。路径都由当前用户的家目录和实际安装位置算出，不写死用户名；不放行整个 `~/.claude/`（里面有会话记录和记忆）。

agy 的 `read_file` 规则语法（agy 1.5.x 实测）：

| 写法 | 结果 |
|---|---|
| `read_file(/abs/dir/**)` | 不认，照样拒 |
| `read_file(/abs/dir/)` | 结尾带 `/`，按目录前缀放行 |
| `read_file(/abs/file)` | 精确放行单个文件 |

agy 按软链解析后的真实路径判权限，所以放行链接所在目录不够，要放行目标目录。这些规则只开读。

## 为什么不用 `--dangerously-skip-permissions`

它会连用户 agy 设置里认为需要确认的操作也一并放行，包括写文件、执行任意命令。去掉 `--mode plan` 已经把普通命令放开了；剩下需要确认的那部分正是风险最高的，没必要再放开。

## 为什么审查者不跑类型检查和测试

- 开发方每轮修改后都会按仓库规则跑这些检查，重复跑收益小。
- 测试和构建脚本会写文件（缓存、产物、快照），会让退出码 4 误报，也可能真的改坏工作区。
- 有的测试要连数据库或外网，审查者那边的环境未必配好。

所以审查者只做静态审查。

## 其他命令行

目前只适配并实测过 `agy`。`cursor-agent` 的无头参数、权限模型和输出格式没有验证过，脚本不会调用它；`check` 在只找到 `cursor-agent` 时会明确提示这一点。要支持它，需要先像上面这样把它的行为实测一遍，尤其是“失败时怎么表现”。
