# 开发与外部审查循环

这个 skill 替用户做一件原本靠手工完成的事：开发会话写完代码后，把改动交给**另一个模型**审查，把审查意见带回来逐条核对、修改，再送审，直到干净为止，最后推送并给出开 PR 的链接。

之所以要外部模型、而不是自己审自己：同一个模型对自己写的代码有盲区，换一个模型、换一份全新的上下文，才能抓到作者习以为常的问题。所以审查一律通过 `scripts/external_review.py` 调用 Antigravity 命令行（`agy`）完成，不要用子代理或自己通读 diff 来代替。

## 流程总览

1. 依赖检查，不通过就停。
2. 确认输入：基准点、规格文件。
3. 开发，提交。
4. 外部审查循环，最多 3 轮。
5. 验收测试（预留，本版本不做）。
6. 推送，给出 PR 链接和汇总。

下文的 `SKILL_DIR` 指本 skill 所在目录，调用脚本时用它的绝对路径。

## 1. 依赖检查

开工前先运行：

```bash
python3 "$SKILL_DIR/scripts/external_review.py" check
```

退出码是 2 时，把它列出的缺失项和安装方法原样告诉用户，然后**停止**，不要开始开发。先查再做的原因是：缺依赖时循环跑不起来，等写完代码才发现，用户就得回到手工传话。

本 skill 依赖两个 skill（`code-review` 和它引用的 `setup-matt-pocock-skills`），以及已登录、能用所选模型的 `agy`。不要替用户安装它们。

## 2. 确认输入

在哪里开发由用户的对话决定：当前目录是什么分支、是不是 worktree，就在那里做。本 skill 不要求功能分支，也不创建、不切换分支或 worktree，除非用户要求。

审查者在无人值守模式下运行，没法向人提问。它需要的两样东西必须在开工前确定：

- **基准点**：diff 相对谁来算。用户指定了就用用户的；否则在功能分支上用 `main`。如果就是直接在 `main`（或别的目标分支）上开发，`main...HEAD` 永远是空的，这时在动手前运行 `git rev-parse HEAD`，把得到的提交记下来当基准点。
- **规格文件**：这次改动要实现什么。必须是审查者能读到的**本地文件路径**（设计文档、工单 markdown 等）。审查者没有 `gh` 之类命令的权限，取不到线上工单；规格只存在于对话里时，问用户是把它落成文件，还是按“无规格”审查（那样 Spec 轴会被跳过）。

能从对话和仓库里确定的就直接用，只有确定不了时才问。

## 3. 开发

按已确认的需求实现，方法遵循仓库自己的规则（`AGENTS.md`、`CLAUDE.md` 等）。本 skill 不规定怎么写代码，只规定出口：

- 需求要求的代码写完，**包括单元测试和集成测试的代码**。
- 仓库规则要求的检查（类型检查、lint、测试）都已通过。
- 全部提交为一个 commit，提交信息遵循仓库规范。

必须先提交再送审：code-review 比较的是 `基准点...HEAD`，没提交的改动审查者看不到。

## 4. 外部审查循环

### 4.1 跑一轮审查

在仓库目录下**后台**运行（一轮通常 2 到 15 分钟，用后台任务等完成通知，不要轮询）：

```bash
python3 "$SKILL_DIR/scripts/external_review.py" run --base <基准点> --spec <规格文件>
```

规格只有某一节相关时加 `--spec-note "第三批 3c 一节"`。没有规格时用 `--no-spec`。默认模型是 `gemini-4-carbon-high`，用户另有指定时加 `--model`。

每一轮都是**全新的对话**、对整个 diff 重新审。不续接上一轮的原因：续接时审查者倾向于只核对“上次那几条修没修”，对修改过程中新引入的问题不敏感；全量重审时，没修好的问题会自己再冒出来。也因此不要把上一轮的结论或你的反驳理由传给审查者。

按退出码处理：

| 退出码 | 含义 | 做什么 |
|---|---|---|
| 0 | 完成 | 读它打印的 `report` 路径 |
| 3 | 审查没跑完 | **不是零发现**。见 `references/reviewer-cli.md`，重试一次，仍失败就停下告诉用户 |
| 4 | 审查者改动了 worktree | 停下，把前后差异告诉用户 |
| 5 | 前置条件不满足 | 按提示修正（多半是没提交）后重跑 |

退出码 3 值得特别小心：`agy` 在审查中途被权限拦下时，自己仍会报告“成功”并返回空内容。脚本已经替你识别了这种情况；如果把它当成“没有问题”放行，就等于没审查就推送了。

### 4.2 逐条核对

读报告。它分两个轴：`## Standards`（硬性违规 / 判断项）和 `## Spec`（a 缺失 / b 多做 / c 不一致）。

对每一条，打开它引用的代码位置和它引用的标准或规格原文，自己核实后判定：

- **成立**：问题确实存在。
- **不成立**：审查者看错了、引用的规则不存在或不适用。写下具体理由。
- **重复**：之前某轮已判定过的同一条。沿用当时的判定，不重复处理。

审查者会出错，所以不能照单全改；但也不要为了让循环早点结束而把成立的条目判成不成立。两种偏差都会让这个流程失去意义。

把判定记到 `<out_dir>/decisions.md`（`out_dir` 在脚本输出里），每条一行：轮次、编号、类别、一句话摘要、判定、处理（commit 或理由）。记到文件而不是只放在脑子里，是因为循环可能很长，上下文被压缩后仍要靠它去重和写最后的汇总。

### 4.3 修改并提交

只改成立的条目及其直接连带（相关测试、要同步的文档）。不顺手重构，不扩大范围：审查之外的改动没人审过，而且会让下一轮的 diff 变大。

改完后跑仓库要求的检查，通过后提交为**这一轮单独的一个 commit**，提交信息正文列出处理了哪些条目。一轮一个 commit 是为了让用户能按轮次审计改了什么。

### 4.4 决定是否再审

把“硬性违规”和 Spec 三类条目称为**阻塞项**；“判断项”不是阻塞项。

- 本轮有成立的阻塞项 → 修改提交后**再审一轮**，确认修好了且没引入新问题。
- 本轮没有阻塞项，或阻塞项全部是“重复”的 → **循环结束**。本轮的判断项照常核对、成立就改并提交，但不为它们再审一轮。

判断项不触发再审，是因为它们带主观性，每个新对话都可能提出不同的几条；让它们参与停止条件，循环可能永远不收敛。

最多 3 轮。第 3 轮结束仍有成立的阻塞项时，停下来交给用户。

## 5. 验收测试（预留）

这里以后会加入前端走查、真实页面操作一类的验收。**本版本不做**，直接进入下一步，不要自行加入浏览器测试。位置放在审查之后，是因为审查会改代码，改之前跑的验收结果不算数。

## 6. 收尾

满足下面全部条件才进入收尾：循环正常结束、没有被你判为“不成立”的阻塞项、最后一次检查通过。

怎么收尾取决于代码在哪里：

- **在功能分支上**（当前分支不是 PR 要合入的目标分支）：推送并给出 PR 链接。用户调用本 skill，就是授权把这个分支推送到远端。

  ```bash
  git push -u origin <当前分支>
  ```

- **直接在目标分支上**（例如就在 `main` 上开发）：没有 PR 可开。用户在对话里说过要推送就推送；没说过就不推，在汇总里说明提交留在本地、等用户决定。直接推目标分支不好撤回，所以不把调用本 skill 当成对它的授权。
- **游离 HEAD**：没有分支可推，不推送，在汇总里给出最后一个提交。

无论哪种情况：不强制推送，不合并，不替用户创建 PR。

然后给出：

- **开 PR 的链接**（仅功能分支）。远端是 GitHub 时：`https://github.com/<owner>/<repo>/compare/<目标分支>...<分支>?quick_pull=1&title=<URL 编码的标题>`。只预填标题，正文放进链接会因为太长而打不开。远端不是 GitHub 时，给出已推送的分支名和目标分支，让用户在自己的平台上开。
- **PR 描述正文**（仅功能分支），放在代码块里，方便整段复制。
- **汇总**，格式见下。

## 何时停下来问用户

出现下面任一情况就不推送，说明情况后等用户决定：

- 依赖检查不通过。
- 基准点或规格确定不了。
- 审查脚本退出码 3 重试后仍失败，或退出码 4。
- 有阻塞项被你判为“不成立”。这是你和审查者的分歧，应该由用户裁决，而不是由作者单方面放行。
- 3 轮后仍有成立的阻塞项。
- 仓库要求的检查失败且修不好。

被判“不成立”的**判断项**不阻止推送，但必须在汇总里列出来。

## 汇总格式

结束时（无论推送与否）用这个结构汇报：

```markdown
## 结果
一句话：推送了没有，卡在哪。

## 各轮审查
| 轮次 | 硬性违规 | 判断项 | Spec | 成立 | 不成立 | 修复提交 |
|---|---|---|---|---|---|---|

## 逐条处理
| 轮次 | 条目 | 判定 | 怎么改的 / 为什么不成立 |
|---|---|---|---|

## 需要你裁决
（没有就写“无”）

## 检查结果
最后一次类型检查、lint、测试的结果。

## PR
链接和描述正文。没有 PR 时写明提交在哪、推送了没有。
```
